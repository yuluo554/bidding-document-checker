## 一、统一中间表示：参数卡（schema v1）

双侧文档解析产物均为 JSON 可序列化的参数卡；Python 侧为 `src/bidchecker/schema.py` dataclasses。

### 1.1 公共结构

```
Evidence（证据）:
  section: str            # 章节定位，如 "第三章 评标办法前附表"
  quote: str              # 原文逐字摘录（必须为原文子串，基准硬校验）
  line: int | null        # 行号（可选）

ProjectInfo:
  name: str | null        # 项目名
  number: str | null      # 项目/招标编号
  buyer: str | null       # 招标人（采购人）
  agency: str | null      # 招标代理机构
```

### 1.2 采购需求参数卡 TenderCard（招标侧）

| 字段 | 类型 | 语义 |
|---|---|---|
| doc_type | `"tender"` | 常量 |
| schema_version | `"1"` | 口径版本 |
| project | ProjectInfo | 项目信息 |
| qualifications | List[Qualification] | 资格资格条件清单 |
| star_clauses | List[StarClause] | 实质性/星号条款（★ 强制、▲ 重要） |
| scoring | Scoring \| null | 评标办法：method（综合评分法/最低评标价法…）+ items[{name, weight}] + price_weight |
| bond | Bond \| null | 投标保证金：amount/currency/forms/deadline |
| key_dates | KeyDates | issue_start（获取）/ submit_deadline（递交截止）/ open_time（开标）/ validity_days（投标有效期） |
| rejection_clauses | List[RejectionClause] | 否决（无效投标）条款清单 |

```
Qualification:
  item_id: str            # 卡内唯一，如 "Q1"
  requirement: str        # 要求原文语义（如 "具备有效 ISO9001 证书"）
  category: str           # qualification|finance|performance|personnel|other
  level: str | null       # 等级要求（如 "一级"）
  valid_until: str | null # 要求的有效期截止（招标侧通常为"投标截止日有效"）
  evidence: Evidence

StarClause:
  item_id: str            # 如 "S1"
  marker: str             # "★" | "▲"
  text: str
  evidence: Evidence

RejectionClause:
  item_id: str            # 如 "R1"
  text: str
  basis: str | null       # 挂法规条号（如 "87号令第37条"）或"招标文件自设"
  evidence: Evidence

Bond:      amount: float|null, currency: str="CNY", forms: List[str], deadline: str|null
KeyDates:  issue_start/submit_deadline/open_time: ISO 日期时间字符串|null; validity_days: int|null
Scoring:   method: str|null, items: List[{name, weight: float}], price_weight: float|null
```

### 1.3 投标响应参数卡 BidCard（投标侧）

| 字段 | 类型 | 语义 |
|---|---|---|
| doc_type | `"bid"` | 常量 |
| project / schema_version | 同上 | 项目信息（用于与招标侧对齐） |
| bidder | str \| null | 投标人名称 |
| qualifications | List[Qualification] | 持有资质/证书/业绩/人员（level=持有等级，valid_until=证书有效期） |
| star_responses | List[StarResponse] | 对星号条款的响应 |
| prices | Prices \| null | 开标一览表与分项报价 |
| bond_response | Bond \| null | 保证金缴纳响应（金额/形式/凭证号） |
| key_dates | KeyDates | validity_days=承诺投标有效期；其余通常 null |
| personnel | List[PersonItem] | 拟投入人员与证书（name/cert_no/cert_name/valid_until） |
| performance | List[PerfItem] | 类似业绩（name/amount/date/counterparty） |

```
StarResponse:
  star_id: str            # 对应 TenderCard.star_clauses[].item_id
  responded: bool
  location: str | null    # 响应位置（章节）
  quote: str | null       # 响应内容摘录
  deviation: str | null   # 偏差描述（商务偏差表口径）

Prices:
  total_words: str | null    # 大写金额
  total_number: float | null # 小写金额
  items: List[PriceItem]     # 分项 {name, amount}
  items_sum: float | null    # 分项合计（算术复核基准）

PersonItem: name/cert_name/cert_no/valid_until
PerfItem:   name/amount/date/counterparty
```

### 1.4 序列化与口径纪律

- 每个 dataclass 提供 `to_dict()` / `from_dict()`，未知键忽略、缺键用默认值（向后兼容）；
- 卡片落盘为 JSON（`output/cards/tender.card.json`、`output/cards/<bidder>.card.json`）；
- **真值语义**（生成器与基准共同遵守）：注入缺陷记**主期望**；同一注入隐含的其余结论记
  `also_expect`；端到端基准按"文档全部非 pass 集合"对账，不是逐条一一比对。

## 二、符合性校核引擎

### 2.1 规则与结论

```
CheckRule（rules.json 机器可读）:
  id: "CHK-Q-01"
  name: "资格条件存在性比对"
  rule_type: qualification_match | star_response | arithmetic_consistency
           | date_logic | bond_check | rejection_scan | price_check
  severity: high | mid | low          # 不符合时的风险分级
  basis: ["87号令第37条", "TenderCard.qualifications[Q1]"]   # 法规条号 + 招标文件条款
  advice: str
  only_if: {keywords: [...]}          # 类目隔离门控（对全部 rule_type 生效）

Finding（结论）:
  check_id: str
  status: "符合" | "不符合" | "待人工确认"      # 三级判定（P0 口径）
  risk_level: "high" | "mid" | "low" | null    # status=不符合时必填
  message: str
  basis: List[str]                              # 依据条款，非"符合"结论必须非空
  evidence: List[Evidence]                      # 命中证据
```

### 2.2 分派与判定纪律

- 引擎按 `rule_type` 分派 handler：`qualification_match`（要求 vs 响应按 category+level 对齐，缺失/
  过期/等级不足→不符合）、`star_response`（逐条核对 responded/location/quote/deviation）、
  `arithmetic_consistency`（total_words ↔ total_number 中文金额换算；items_sum ↔ total_number）、
  `date_logic`（validity_days ≥ 要求；递交截止/开标时间顺序）、`bond_check`（金额/形式/时限）、
  `rejection_scan`（对照 rejection_clauses 与 87 号令否决情形逐项排查）、`price_check`（低于成本/最高限价提示）；
- **数值与布尔类结论只由规则产生**；文本语义类规则可判则判，不可判 → `待人工确认`（不硬判）；
- **类目隔离门控**：`only_if.keywords` 命中输入文本才激活规则，门控对**全部** check_type 生效
  （conditional/checklist 分支同样过门控——跨类目误查参数是实测踩过的坑）；
- 每条 Finding 的 `basis` 必须能解析回知识库条文块或 TenderCard 条款 id（依据关联率 100% 的实现基础）。

## 三、解析器设计（规则优先）

```
parse(text) 流水线：
  1) 预处理：CRLF 归一、伪空格清理（零宽字符/全角空格定位）、行号索引
  2) 章节切分：固定体例标题正则（"第X章"、"（一）"等）→ section 树
  3) 槽位抽取：字段级正则 + 槽位函数（金额中文换算、日期归一化、等级词表）
  4) 合法性校验：数值范围/日期顺序/枚举值，不合法即丢弃该抽取（宁缺勿错，留待 LLM 兜底或人工）
  5) 证据绑定：每个槽位记录 section + 原文子串摘录 + 行号
```

- LLM 兜底（M4，可选通路）：只对规则抽取失败的槽位，输入**候选行压缩**后的行集合，要求返回
  `{field, value, quote}`；quote 非原文子串即丢弃；数值过合法性校验才入卡；
- 每个解析器配生成器产出样例做回归测试（M2 起，fixtures 字节冻结）。

## 四、知识库（三层）

```
data/knowledge/
├── raw/            # 法规原文 txt（来源台账：URL+获取日期+sha256）
├── blocks.jsonl    # 条文块：{law, article_no, text, source_url, status: 已核对|待核对}
└── rules.json      # 机器可读规则表（CheckRule[]，阈值/否决情形映射）
```

- 检索：`knowledge/search.py` TF 余弦 top_k（不引向量库）；
- 入库纪律：条文以官方原文为准（国家法律法规数据库 flk.npc.gov.cn、政府/部委官网），逐条挂
  出处与 status；**查不到 → status=待核对 + 显式落库，不得以确定语气写进结论**；
- 围标依据：《招标投标法实施条例》第 39/40 条情形 → `rules.json` 里映射为文本特征检查项（挂条号）。

## 五、围标串标文本特征（P1）

- **相似度**：字符 5-gram shingle + Jaccard，两两矩阵（N 份投标，N≤10 规模足够）；
- **异常一致性**：相同错误字符串（同一处错别字/同一格式错误）、相同模板句（长公共子串）、
  相同编制特征（同一非常用词组合）；仅文本特征，不做主体关系推断；
- **图谱 HTML**：自绘 SVG 力导向布局，节点=投标人，边=相似度/一致性问题（标注类型与证据数），
  点击节点/边 → 展开证据文本与锚点（溯源联动）；硬断言 0 外链；
- 输出为**辅助提示**（挂 39/40 条情形），结论级别仅"待人工确认"或提示性说明，不出"围标"定性结论。

## 六、编排与 CLI

```
pipeline 状态机节点：load → parse_tender → parse_bids → checks → collusion(可选) → aggregate → report(可选)
每节点记录耗时与产物路径；单节点失败 → 失败清单落盘，不中断其余节点（可解释的降级）。

CLI（bidchecker）：
  run <项目目录>            # 端到端：双侧解析 → 校核 → 输出 findings JSON + 摘要
  datagen --seed N --out D  # 合成数据生成（M1）
  bench parse / bench e2e   # 基准（M2/M4）
  report <findings.json>    # docx 报告（M5，需 report extra）
  serve [--port]            # Web 面板（M5，需 web extra）
```

## 七、评测基准设计

| 基准 | 输入 | 对账 | 指标 |
|---|---|---|---|
| bench parse | 生成器项目 → 两侧文档 + 字段级真值 | 逐字段：抽取值+证据 vs 真值 | 按字段类别的 P/R/F1 + 总体 F1 |
| bench e2e | 生成器配对集（含注入缺陷 + 干净对照） | 主期望 + also_expect 全集合 vs findings 非符合集合 | 检出率（分缺陷类型）/ 误报数 / 判定准确率 |

门槛（题目评分口径）：F1 ≥ 0.95；检出率 ≥ 0.95；干净对照误报 = 0；全程零 API、固定 seed 可重复。
